The authorized next task owns `relationship_*`, `test_relationships.py` and private `KnowledgeBase/library-knowledge/connected-research/relationships/`. It reads pinned KR-101/102 and the completed KR-110 located candidate release, without consuming KR-110's failed question ranking. All 100,889 supported parent documents are accounted; only native/recorded section windows enter relationship processing. Candidate headings, document fallback, short/unsegmented text, common fingerprints and inherited adapter exclusions remain explicit. This is independent of the expansion from the already embedded 8M to the newer 11M corpus. Semantic neighbors are deferred; this processor selects no vectors and starts no encoder, intake, graph writer, scheduler or deployment.

Word tokens preserve Unicode accents, casefold and map long s, ignoring punctuation/spacing. Sixteen-token fingerprints are winnowed across 64 consecutive shingles, guaranteeing a selected shared fingerprint for an identical normalized run of at least 79 tokens when wholly inside each window. Shorter matching runs can be missed. SHA256 keys and original substring hashes retain evidence; normalized equality is not exact byte equality. Artificial window boundaries are retained and can split reuse. This method finds textual-overlap candidates, not paraphrase or translation similarity.

Reference features retain exact canonical book/range and original located reference witnesses. A shared reference is a single-citation association; at least two distinct shared ranges are required to call a pair co-citation. Overlapping but differently expressed ranges are not silently equated. Reference mentions are not exposition.

`relationship_cocitations.py` is a separately versioned derived pass over the completed posting generation. It indexes pairs drawn from the first 12 distinct located ranges in each reference-bearing window, then applies the 32-posting/two-per-group bound to the **joint signature**. Thus two individually common verses may yield a supported rare combination. The base single-reference associations remain available. Joint runs pin the complete parent contract/summary and retain their own atomic batch/bucket jobs and checkpoints. Calibration uses only development known-pair endpoints; reserved cases are not used for tuning. Run `relationship_cocitations --calibrate`, verify with `relationship_verify --joint-calibration`, then run `relationship_cocitations` (add `--resume` after interruption). `--limit-batches` provides a deliberate checkpoint stop. Queries and releases pin both base and joint generations.

Pair queries reconstruct both source windows and extend the fingerprint anchors into monotone equal-token islands of at least eight words using bounded SequenceMatcher alignment. Changed words and gaps remain unmatched. Returned spans distinguish exact literal equality from normalized-token equality. This on-demand alignment is not a claim that complete works, translations or every pair in the population have been aligned.

Neighbor retrieval uses separate indexed left/right endpoint lookups. The original OR predicate searched the whole selected generation; `relationship_query_plans` records the actual SQL plans, and `relationship_query_equivalence` compares ranked rows against the preserved pre-optimization SQL, including high-degree cases. Run both after the full base and joint populations complete, before freezing the evaluation pool. This equivalence proof concerns the endpoint optimization, not acceptance of a future changed ranking method. Query/helper code hashes and Python/SQLite/Unicode/parser versions bind the pool and release; a selected query with changed dependencies fails closed. Helpers are copied into the immutable code snapshot.

To avoid quadratic comparisons, features with more than 32 window postings are retained and counted but excluded from pair generation. At most two windows per known-work or unresolved original-byte group participate in each bounded feature. All eligible features are indexed, not a tiny document sample. Same-group pairs are excluded. Unknown work independence remains unresolved; different source bytes are not proof of different works. Common Bible wording, repeated editions, editorial apparatus and translation relationships require explicit review. Neither chronological direction nor author endorsement/influence is inferred.

Facts and checkpoints commit atomically through existing JobStore/global and local leases. Source/section/metadata/config/code and full parent-release dependencies bind each generation. Population-dependent frequency and neighbors rebuild for a changed generation. Same-generation resume reuses committed jobs. Cross-generation selective refresh and backup restoration are not claimed. Old releases and source files remain intact. Atomic candidate pointer selection occurs only after structural verification, measured quality reporting and immutable exports.

The measured operational wrapper `relationship_run --resume --cache-mib 16384 --document-batch 256 --checkpoint-pages 262144` uses the identical generation and job IDs, groups at most 256 document callbacks with per-job savepoints, and caps the derived SQLite cache at 16 GiB. Its WAL checkpoint threshold is 262,144 pages (1 GiB at the observed 4 KiB page size); a transaction can exceed the threshold. Earlier 512 MiB/4 GiB caches and 16/32-document attempts are retained. The larger cache was selected after observing low CPU use, a full 4 GiB cache and about 80 GiB available on the 128 GiB host. Commit/checkpoint bounds were adjusted after measuring repeated writes far above output growth. Throughput is measured, not assumed. The shared JobStore extension accepts an explicit `max_jobs` up to 256 while retaining the existing default of 32; other callers are unchanged. Its large-group abort/rollback/resume and tail-discard tests pass, alongside existing actual-process-crash and competing-owner tests. There is one below-normal-priority writer. A stopped partial group is discarded and resumed normally. The base miner remains valid; the wrapper changes commit/cache behavior, not feature rules or reserved evaluation. Launch identities, JobStore/wrapper hashes and resource samples are retained.
