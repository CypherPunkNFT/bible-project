## 5. Implement and execute

Implement the smallest vertical unit that returns real source sections/evidence, then run all supported inputs after a representative source-type calibration. Keep unsupported/ambiguous cases explicit. Use focused tests for identity, alignment, attribution, changed inputs and recovery; do not generate per-file check suites.

Use native Python/Node commands through cmd.exe with login disabled under the current Windows launch instructions. Do not introduce encoded PowerShell wrappers or antivirus exclusions. Dependency visibility can differ between the restricted sandbox and the owner's normal Python environment; report that distinction and use existing approved access rather than fake successful integration with missing dependencies.

Prefer one bounded, low-priority analytical worker until measured resources justify more. Commit derived facts and checkpoints together. Reuse completed fingerprint-matching jobs. Never use a completed historical generation as a mutable working run.

Build source/version dependency tracking, changed/removed input handling, idempotence and same-generation recovery into each new processor from the start. The future-additions protocol requires cross-generation reuse, population-dependent rank/neighbor updates, compatible release manifests and consistent backup/restore proof. These are implementation requirements, not capabilities established by the protocol document. Do not call local file persistence an off-device backup or mark a historical release current for newly acquired texts.

For long work, record command, working directory, PID plus creation identity, lease/checkpoint owner, progress/log paths, processed/eligible counts, throughput, remaining work and resume/cancel commands. Checkpoint and release requirements apply to analytical jobs; do not modify embedding/watchdog recovery as a convenience.
